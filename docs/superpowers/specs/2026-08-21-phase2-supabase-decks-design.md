# Phase 2 — Supabase-backed deck downloads — Design

**Source:** Brainstorming session with the project owner, 2026-08-21, following up on the Phase 1 refactor (`docs/superpowers/plans/2026-08-20-phase1-refactor-*.md`), whose spec explicitly reserved this as a later, separate initiative.

## Goal

Stop bundling the 44 base decks' content (words/sentences) inside the app binary. Ship only a lightweight catalog (names, categories, word counts) locally; fetch a deck's actual content from Supabase the first time the user picks it, then cache it locally for offline reuse.

## Explicitly out of scope for this pass

- Authentication, user accounts, login flows.
- Syncing user data (progress, custom decks, review history, settings) to Supabase — these stay exactly as they are today, local-only via `SharedPreferences`.
- Sharing/publishing custom decks between users.
- Versioning or update-checking for already-downloaded deck content (a manual pull-to-refresh re-fetch is enough for now).
- A bundled "starter" deck for a fully offline first launch — installing the app already requires network, so requiring network to download the first deck is acceptable.
- Updating the `add-deck` skill's workflow instructions for the new seed-to-Supabase step (a follow-up, not part of this implementation).

These are deliberately deferred, not forgotten — sync/auth/sharing were flagged by the project owner as likely future work once this pass lands.

## Current state (what this replaces)

- `assets/decks/manifest.json` lists 44 decks with `path`, `categories`, `difficulty` only. `DeckRepository.loadBaseDecks()` reads every deck's full JSON file from the asset bundle (via `rootBundle.loadString`) to get `id`, `name`, `words`, `sentences`, `inputType`, etc.
- `DeckCard` (browsing UI) reads `deckProvider.repository.getDeckMetadata(deck.id)` — a `DeckEntry` — for the difficulty chip, but reads word count and input type from the fully-loaded `Deck` object directly.
- `DeckProvider.selectDeck(Deck deck)` is synchronous: it just assigns `_selectedDeck` and persists the id.
- Deck content (words/sentences) never needs network today — everything is bundled.

## Data model & Supabase schema

**`assets/decks/manifest.json`** (`DeckEntry` in `lib/data/models/deck_manifest.dart`) gains new required fields, generated by `tool/generate_deck_manifest.dart` from the source JSON files at build time:
- `id: String` (currently only inside the full deck JSON)
- `name: String`
- `inputType: String`, `reverseInputType: String?`
- `wordCount: int`
- `hasSentences: bool`

`DeckRepository.loadBaseDecks()` builds `Deck` objects directly from these manifest fields, with `words: []` and `sentences: []` (no asset file reads, no network). The `Deck`/`Word`/`Sentence` Dart models themselves are unchanged.

**Supabase**: one table, `decks`:
- `id text primary key`
- `content jsonb not null` — exactly `{"words": [...], "sentences": [...]}`, the same shape `Deck.fromJson`/the source JSON files already use for those two fields.
- Row Level Security: public `SELECT` for the `anon` role, no `INSERT`/`UPDATE`/`DELETE` for `anon` (content is maintained by the developer via the seed script, not by end users).

## Client & credentials

Add the `supabase_flutter` package (official SDK) as a new dependency, initialized once in `main.dart` with the project URL and `anon`/publishable key. This key is safe to embed client-side (protected by RLS, not a secret like the `service_role` key) and is kept in a single constants location rather than scattered through the code. Using the official SDK now — rather than raw `http` calls against the PostgREST endpoint — costs nothing extra today and avoids a dependency swap when the already-planned future auth/sync work arrives.

## Repository & provider changes

`DeckRepository` gains:
- `Future<Deck> downloadDeckContent(String deckId)`: fetches the `decks` row for `deckId` from Supabase, parses `content` into `words`/`sentences`, merges them into the matching metadata-only `Deck`, persists the result locally under a `downloaded_deck_<id>` key (same JSON-string storage pattern `saveProgress`/`saveCustomDecks` already use), and returns the populated `Deck`. Throws on network/parse failure — callers decide how to surface it.
- The Supabase query itself sits behind a small constructor-injectable function (`Future<Map<String, dynamic>?> Function(String id) fetchDeckContent`, defaulting to the real Supabase call), so tests can substitute a fake without a live project or a mocking framework — consistent with how the rest of the test suite avoids mocks.
- `loadBaseDecks()`, after building the metadata-only list, checks for a `downloaded_deck_<id>` cache per deck and merges it back in immediately if present — a previously-downloaded deck is fully usable offline on the next launch, no re-fetch needed.

`DeckProvider.selectDeck(Deck deck)` becomes network-aware:
- If `deck.type == DeckType.base && deck.words.isEmpty && deck.sentences.isEmpty` (no content loaded or cached yet): set a `_downloadingDeckId` field, notify listeners, call `repository.downloadDeckContent(deck.id)`, then either update the deck in `_baseDecks`/select it (success) or leave it unselected and surface an error (failure) — always clearing `_downloadingDeckId` afterward.
- Otherwise (already has content, or is a custom deck): behaves exactly as today, synchronously.
- New getter: `bool isDownloadingDeck(String deckId) => _downloadingDeckId == deckId`.

## UI changes

`DeckCard`:
- Reads `wordCount`/`hasSentences` from the (now-enriched) `DeckEntry` metadata for base decks, instead of `deck.totalWords`/`deck.sentences.isNotEmpty` — so an undownloaded deck still displays correct counts.
- Shows a cloud-download icon instead of the keyboard/draw icon when a base deck has no content loaded/cached yet; swaps to a small spinner while `deckProvider.isDownloadingDeck(deck.id)` is true; falls back to the current keyboard/draw icon once content is present.
- On download failure, a snackbar with an error message (same pattern as the existing "no deck selected" snackbar) — tapping the card again simply retries, no separate retry affordance.

The home screen's existing "Phrase" mode card disabling (added in the reset-per-mode work) reads `selectedDeck.sentences.isEmpty`, which is always true for an undownloaded base deck regardless of whether it actually has sentences — that check needs a small update to read the manifest's `hasSentences` for base decks instead, falling back to `sentences.isEmpty` only for custom decks (always fully loaded, no manifest entry).

## Rollout

- `tool/generate_deck_manifest.dart` updated to emit the new manifest fields.
- New `tool/seed_supabase_decks.dart` script reads every source JSON file and upserts its `id`/`content` into the Supabase `decks` table — run manually whenever a deck is added or edited. Requires the Supabase project URL and a key with write access (the `service_role` key, used only locally/in this script — never shipped in the app).
- The 44 JSON files stay in the repo (source of truth for the manifest generator and the seed script) but are removed from `pubspec.yaml`'s `assets:` list so they stop shipping in the app bundle.
- No user-data migration needed — this only affects static app content, not anything stored per-user.

## Testing

- `DeckRepository` unit tests: inject a fake `fetchDeckContent` to verify `downloadDeckContent` parses/caches correctly, and that a failure propagates instead of silently returning an empty deck.
- `DeckProvider` unit tests: verify `selectDeck` on a content-less base deck sets `isDownloadingDeck` during the fetch and clears it after, for both the success and failure paths.
- No widget/integration tests for `DeckCard`'s new visual states, consistent with this repo's existing convention (screens/widgets aren't covered by automated tests; verified via `flutter analyze` + `flutter test` plus a manual pass if requested).
